## Findings

### F1. The 8-player cap is not enforced on the server (Medium)

Where:

- `app/controllers/players_controller.rb:22-36`: `create` saves whatever color is posted. `free?`, `full?` and `PRESET_COLORS` (`:2`, `:50-54`) only pick the default and feed the view's "This room is full" (`app/views/players/new.html.erb:8,57`)
- `app/models/player.rb:7`: `color` must be any `#RRGGBB` and unique in the game. 16.7 million colors, so no cap
- `db/schema.rb:54-68`: no unique index on `(game_id, color)`, so even the uniqueness is a read-then-write check
- `app/controllers/players_controller.rb:7`: 20 joins a minute per IP slows this, it does not bound it
- `app/models/player.rb:12,39-41` and `app/models/game.rb:85-100`: each join renders one `players/controller_status` per player already in the room, inside the request
- `app/models/game.rb:27,239-267`: every `Game#update!` does the same, plus five big screen partials, synchronously in `after_update_commit`. Each player's partial lists every player (`app/views/players/controller/_scoreboard.html.erb:6`, `_roster.html.erb:3`, `_standings.html.erb:4`), so one update costs N renders of N rows
- `config/cable.yml:12-17`: each broadcast is a row in the cable SQLite database, kept a day, on the VPS shared with two other apps (`config/deploy.yml:11`)
- None of `/ready`, `/claims`, `/no_set`, `/end_game` is rate limited

SPEC §10 says "Player colors are the 8 presets" and §8 sizes every screen for 8 players.

Scenario: someone opens a room of their own (no victim's code needed), loads the join page once for a CSRF token, then posts `player[name]=a1&player[color]=#000001`, `a2` / `#000002`, and so on, 20 a minute from one address, more from several. After 30 minutes the room holds 600 players. From then on each unthrottled POST that updates the game (a ready vote, a claim, a wrong Submit) renders 600 player screens of 600 rows each in a Puma thread and writes 600 broadcast payloads to the cable database. Puma has 3 threads (`config/puma.rb:28`) in the one container that also runs the jobs (`config/deploy.yml:42`), so every room stalls, and the cable database grows on the disk the other apps use. The same posts aimed at a stranger's waiting room (the code is on their big screen) break its 8-player layouts and stop the ready vote from ever completing, since `vote_start!` waits for every player (`app/models/game.rb:63`).

Not run: the cost is read from the code, not measured. The model accepting a non-preset color is also what the existing specs rely on (`spec/requests/players/controller_spec.rb:27` creates a player with `#3498DB`, not a preset).

Suggested fix:

1. Refuse a join whose color is not a free preset: validate `color` against `PlayersController::PRESET_COLORS` on create (move the list to `Player`), which with the uniqueness rule caps a room at 8. The planned bots (SPEC, AI opponent) already take "the first free color", so they fit the same cap
2. A unique index on `players (game_id, color)`, so two joins at once cannot share a color and slip past the cap
3. Request specs: a non-preset color is refused, a ninth join is refused
4. Worth considering in the same ticket: a `rate_limit` on the gameplay POSTs, per player

### F2. No Content-Security-Policy (Low)

Where: `config/initializers/content_security_policy.rb:7-29` is all comments, so no `Content-Security-Policy` header is sent and `csp_meta_tag` (`app/views/layouts/application.html.erb:11`) renders nothing. The layout loads a stylesheet from `fonts.googleapis.com` (`:22-24`) and the telemetry tags (`:26`).

Scenario: none today. No view, helper or Stimulus controller outputs user text unescaped (see Checked, below), so this is the missing second line of defence: if a later change introduced an injection, nothing would stop the injected script from running or from sending data anywhere.

Suggested fix: turn the policy on in report-only mode first, then enforce. Roughly: `default-src 'self'`; `script-src 'self'` with a nonce for the importmap and whatever `jt_telemetry_tags` emits; `style-src 'self' https://fonts.googleapis.com` plus `style-src-attr 'unsafe-inline'` for the player color `style=` attributes; `font-src https://fonts.gstatic.com`; `connect-src 'self'` plus the PostHog and Sentry hosts; `frame-ancestors 'none'`; `base-uri 'self'`; `form-action 'self'`. The nonce generator in the commented template uses `request.session.id`, which is empty for a visitor with no session: use a random nonce per request instead. jt-playbook should carry the policy as a shared convention.

The other headers are in place through Rails defaults, which no config here overrides: `X-Frame-Options: SAMEORIGIN`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, and HSTS through `force_ssl` (`config/environments/production.rb:27-29`).

### F3. Room codes and shuffles use a non-cryptographic generator; code lookups are not throttled (Low)

Where:

- `app/models/game.rb:287`: `CODE_ALPHABET.sample`, Ruby's default Mersenne Twister. `app/models/game.rb:30,36`: the deck `shuffle` uses the same generator
- `app/controllers/lobbies_controller.rb:8-13` (`/join?code=`), `app/controllers/games_controller.rb:15` and `app/controllers/players_controller.rb:13-20`: no `rate_limit`, each answers differently for a live code and a dead one

The room code is the only thing between a stranger and a room: with it they see the big screen and the roster, and join while the room is waiting. It is 6 characters of 32, about 1.07 billion values.

Scenario, guessing: with a handful of live rooms a blind guess hits about once in 200 million tries. Unthrottled, that is still weeks of requests for one random room, so not a practical attack today. It becomes one as live rooms grow.

Scenario, prediction: every code the server issues is 30 bits of generator output, and anyone can collect codes by starting rooms (10 a minute, `games_controller.rb:3`). A Mersenne Twister's state can be rebuilt from enough observed output, after which the next room codes and the next deck orders are predictable: joining rooms as they are created, or knowing which cards come next in a game one is playing. Read from the code and the generator's known weakness; not demonstrated here, and other requests drawing from the same generator make it harder.

Suggested fix: `CODE_ALPHABET.sample(random: SecureRandom)` and `shuffle(random: SecureRandom)` (three call sites), and a `rate_limit` by IP on `lobbies#join` and on the per-code GETs.

### F4. `config.hosts` is unset (Low)

Where: `config/environments/production.rb:80-87` (commented out). The join QR, the copied invite link and the "or open ..." line are built from the request's host: `app/helpers/games_helper.rb:2-14`, `app/views/players/controller/_invite.html.erb:4,9`. Broadcasts are safe, they use the fixed host (`production.rb:59`), and the canonical link is hard-coded for this reason (`app/helpers/application_helper.rb:2-4`).

Scenario: none today. A forged host only changes the page sent back to the forger, since HTML responses are private and nothing caches them for others. It turns into a real hole the day a link built from the request reaches someone else: a shared cache in front, or the v1.5 magic-link emails (SPEC §14), where a forged host puts the attacker's domain in the victim's sign-in link.

Suggested fix: `config.hosts = ["onset.joaotorr.es"]` with `/up` excluded, as the commented lines show. Do it before any mailer is added.

### F5. Host actions do not check the game's state (Info)

Where: `app/controllers/games_controller.rb:19-33`, `app/models/game.rb:29-32`. `start` checks the `host_game` cookie and the player count, not that the room is waiting, and `start!` takes no lock; `restart` runs in any status.

Scenario: the host's own browser posts `/games/CODE/start` mid-game. The board and deck are reshuffled, the scores kept and a running claim left pending against cards no longer on the board. Only the host can do it, so no privilege is crossed: a game-integrity bug, listed because "admin-only actions" was on the checklist. The authorization itself is right: both actions answer 403 without the cookie.

Suggested fix: inside `with_lock`, `start!` returns unless `waiting?`, and `restart!` returns unless `ended?` (or whatever §6 allows).

### F6. CI actions pinned by tag; the auto-merge workflow holds a write token (Info)

Where: `.github/workflows/dependabot-auto-merge.yml:7-9,18` (`contents: write`, `pull-requests: write`, `dependabot/fetch-metadata@v3`), `.github/workflows/ci.yml:14,17,56,87`.

Scenario: a moved tag on one of these actions would run new code with that workflow's token. The workflow is on `pull_request`, not `pull_request_target`, runs only for Dependabot's PRs and only turns on auto-merge for minor and patch updates after a cooldown; a merge still deploys nothing without `bin/deploy`. Standard practice, low exposure.

Suggested fix: pin the actions to commit SHAs (Dependabot keeps them current), at least in the workflow with the write token.

## Checked, nothing found

- **Sessions and cookies.** `player_token` is `SecureRandom.hex(16)`, 128 bits (`app/models/player.rb:44`), minted on the server at join and never accepted from the client, so there is nothing to fixate. Both identity cookies are encrypted, `httponly`, `same_site: :lax` (`players_controller.rb:29`, `games_controller.rb:10`); `Secure` is added to every cookie by `force_ssl` in production. `theme` and `card_colors` are written by script, hold no identity and are read through an allow-list (`app/helpers/themes_helper.rb:9,15`)
- **CSRF.** On by default (`load_defaults 8.1`), no `skip_forgery_protection` anywhere, off only in `config/environments/test.rb:29`. The one hand-written `fetch` sends the token (`card_selection_controller.js:26-36`). Every state change is a POST, PATCH or DELETE; `/join` is a GET that only redirects
- **Authorization and IDOR, every controller.** Player actions load the room by code, then the player through `@game.players.find_by!(session_token:)` (`claims_controller.rb:53-57`, `no_sets_controller.rb:30-34`, `end_games_controller.rb:16-20`, `controllers_controller.rb:3-6`, `games_controller.rb:36-37`), so a cookie from one room does nothing in another. A request with no cookie matches no player: `session_token` is `NOT NULL`. A claim is looked up inside the room and must belong to the caller (`claims_controller.rb:32-37`), 403 otherwise. Host actions check `host_game` against the room's code (`games_controller.rb:20,28`). The big screen and join page are open to anyone with the code, by design (SPEC §8)
- **Realtime.** Only Turbo's signed streams, no custom channel. `player:<id>` is handed out only on that player's own screen (`app/views/controllers/show.html.erb:2`), and Action Cable keeps its same-origin check
- **SQL injection.** Two string conditions, both with bind parameters (`game.rb:114`, `player.rb:50`). Brakeman agrees
- **XSS, views and JSON.** No `raw`, no `<%==`, no `innerHTML`. The three `html_safe` calls wrap constants or the QR library's SVG (`cards/_card.html.erb:15`, `layouts/_settings.html.erb:59`, `games_helper.rb:7`). Player colors go into `style=` only after `\A#[0-9A-Fa-f]{6}\z` (`player.rb:2,7`). JSON reaches the page through `tag` data attributes, which escape it (`tracking_helper.rb:4,11-17`)
- **Header injection.** The only headers set are constants (`application_controller.rb:18`, `clocks_controller.rb:5`)
- **Mass assignment.** One permit list, `params.expect(player: [:name, :color])` (`players_controller.rb:68`); `mode` is mapped by hand (`games_controller.rb:9`); card ids are coerced to integers and checked against the board (`claims_controller.rb:41-47`, `claim.rb:52-58`)
- **Open redirects.** Every `redirect_to` takes a path helper fed from the database. The How to play back link accepts only a well-formed room code (`lobbies_controller.rb:17-19`)
- **Rate limits.** Room creation 10 a minute and joins 20 a minute per IP, stored in Solid Cache (`production.rb:45`). Gaps are in F1 and F3
- **Secrets.** `.kamal/secrets` holds three names (`KAMAL_REGISTRY_PASSWORD`, `SENTRY_DSN`, `RAILS_MASTER_KEY`), each a command or variable reference, no literal value (checked by pattern, values not printed). `config/*.key` and `.env*` are ignored and were never committed in any branch. No secret in `app/`, `config/` or the workflows. The only app log line is `near_tie` with the room code and player ids (`game.rb:274`), no token; `filter_parameters` covers `token` and the usual names
- **Container.** Runs as uid 1000, not root (`Dockerfile:66`)
