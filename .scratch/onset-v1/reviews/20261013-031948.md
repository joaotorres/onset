## Pending decisions

1. **A pick made just before the player screen redraws can be lost from the screen but still count.**
   While a player is choosing 3 cards, their screen can be redrawn by something
   else (for example the end of a previous claim's flash). If a tap's request is
   still on its way when that happens, the redrawn screen shows the picks from
   before the tap, while the old page code still sends the tap once the earlier
   request returns. If the player then stops tapping, the claim is judged on 3
   picks while the screen shows 2 of 3, or the reverse. Ticket 19 decided "a
   redraw renders the picks from the server" and SPEC §11 says the controller
   "continues from them"; this race leaves a gap in that. Rare: it needs a redraw
   inside the fraction of a second a request takes.
   - **Recommended: fix it in a small ticket.** The page code keeps the latest
     selection per claim across a redraw, so the redrawn screen shows the newest
     picks and the server gets the same. Players would notice nothing except
     that the case stops happening. Cheap now, no data or schema change.
   - Leave it: players may very occasionally see a claim judged on picks the
     screen did not show. Fixing it later costs the same.

   `/skills-loop:request "A tap made just before the player screen redraws during a claim reaches the server but not the redrawn screen; keep the latest picks across the redraw"`

(c) Implemented but questionable:
1. **Redraw during an in-flight pick** (user-noticeable, rare): see Pending
   decision 1. The old controller instance keeps no `disconnect()` and its
   `finally` flushes its own `this.selected` when `dirty`
   (`card_selection_controller.js:82-87`), while the new instance rebuilt its
   picks from HTML rendered before that flush. No spec covers taps overlapping
   a redraw.
2. **Picks against expiry: correct.** `pick!` takes `game.with_lock` then
   `reload.pending?` (`claim.rb:26-27`), as `ExpireClaimJob` does. A pick after
   expiry answers 204 and is ignored, matching §11 "a tap still in flight is
   lost". The `fetch` response is never checked, so a 403 or 422 drops picks
   silently; the spec is silent on errors.
3. **Lockout countdown: correct.** Start, duration and digits all read
   `CLAIM_TIMEOUT` (`_controller_status.html.erb:161-165`); `lock_out!` uses it
   for `locked_until` and the `UnlockBroadcastJob` wait (`claim.rb:80,83`).
4. **Footer offset: correct.** Columns `minmax(0,1fr)_248px` with
   `lg:gap-x-8`: board centre W/2 - 140, and `mr-[280px]` gives the same. Below
   `lg`, and in waiting and game over (no `[data-board]`), the footer stays
   centred on the screen.
5. **Minor, not user-visible.** `card_ids_valid` allows 0 to 3 picks while
   expired; only fewer than 3 occur, consistent with §4.
