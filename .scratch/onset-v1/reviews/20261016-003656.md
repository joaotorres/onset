Edge cases checked:

- **Redraw for a different claim, or the claim ending:** a new URL replaces the
  stored state (`:14`); a late resend to the old URL is ignored by `pick!`
  because that claim is no longer pending. Correct, though no example covers a
  claim with picks ending and a new one starting on the same page.
- **Page reload:** memory is gone and the server's picks win, as §11 says.
- **Two tabs, and a failed request:** a deliberate trade-off of ticket 23
  (memory wins within the same claim). A tab that did not make the latest pick
  keeps showing its own picks after a redraw; a pick whose request failed
  (`:41`) stays on screen though the server lacks it, so a player who stops at
  3/3 can get Time's up. §11's promise ("the pick that is sent next is the
  selection the screen shows") holds, retries are Out of scope, and both cases
  need two tabs or a dropped request. Not a pending decision.
